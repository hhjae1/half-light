# HALF-LIGHT — 기술 설계 노트 (보고서용)

강의 개념과 구현을 매핑한 기록. 보고서 작성 시 근거 자료로 사용.

## 충돌 처리: 수동 AABB 선택 (BVH/물리엔진 미사용)

**방식**: 맵의 모든 정적 장애물(벽·기둥·상자·드럼)을 생성 시 `THREE.Box3`(축 정렬 경계 상자, AABB)로 등록하고, 플레이어/좀비가 매 프레임 자기 위치를 반경(radius)과 함께 박스 배열과 비교한다. 이동은 X축·Z축을 분리 검사해 벽에 부딪히면 미끄러지게(slide) 처리.

**BVH(`three-mesh-bvh`)나 물리엔진(cannon/rapier)을 쓰지 않은 이유**:
- 맵 지오메트리가 전부 **박스/평면 primitive**라, 삼각형 단위 충돌이 필요 없다. AABB vs 점(반경) 검사로 정확히 충분하다.
- BVH는 **고폴리곤 임의 메쉬**에서 광선/충돌을 가속할 때 의미가 있는데, 본 게임엔 그런 메쉬가 없어 도입 시 복잡도만 늘고 이득이 없다.
- AABB는 **O(콜라이더 수)** 의 단순 비교라 더 가볍고, 디버깅/튜닝이 쉽다(통로 폭·끼임 등을 좌표로 직접 조정 가능).
- 물리엔진은 강체 시뮬레이션이 목적인데, 본 게임은 "막힘/미끄러짐"만 필요해 과한 의존성이다.

**트레이드오프**: 동적 객체끼리(좀비↔좀비)의 충돌은 자동으로 처리되지 않음 → 별도의 분리(separation) 로직으로 해결(아래).

**관련 파일**: `player.js` `_blocked()`, `enemy.js` `_blocked()`, `room.js`의 `colliders`.

## 길찾기: 격자 A* (nav.js)

- 콜라이더를 에이전트 반경만큼 부풀려 점유 격자(occupancy grid) 생성, 8방향 A*(octile heuristic, 코너 컷 방지).
- WebGL엔 내장 내비메시가 없어 직접 구현. 미로/특수통로 변경 시 콜라이더만 바꾸면 자동 반영.
- 좀비는 점프/포복을 못 하므로, 특수통로(점프 장벽·개구멍)는 nav에서 막힘으로 처리 → 플레이어 전용 지름길.

## 좀비 AI: 역할 분담 추격 (flanking)

- 감지(시야각 FOV + 거리 + 가시선 LOS, 소리 청취, 손전등 피격) → 추격/수색/배회 상태.
- 여러 마리일 때 **같은 점으로 몰리지 않도록 역할 분담**: 한 마리는 플레이어 위치로 직접, 다른 마리는 측면/길목으로 우회시켜 **양옆에서 몰아가는** 느낌 부여.
- 좀비 간 **분리(separation)** 로 겹침 방지.

## GI: probe 격자 DDGI (gi.js)

### 접근: 레이트레이싱을 CubeCamera 래스터화로 대체

**DDGI 원본**(강의)은 각 probe에서 **레이트레이싱**으로 주변 radiance를 수집한다("ray tracing from each probe"). 광선마다 "어느 삼각형에 맞나"를 찾아야 하므로, 고폴리곤 씬에서는 **BVH(Bounding Volume Hierarchy)로 광선-삼각형 교차를 가속**하는 것이 일반적이다(하드웨어 RT 코어도 내부적으로 BVH 사용).

**WebGL 제약**: WebGL은 **래스터화 전용 API**로, 하드웨어 레이트레이싱 파이프라인(DXR, Vulkan RT 등)을 노출하지 않는다. 셰이더 안에서 소프트웨어 레이트레이싱을 흉내낼 수는 있으나 느리고 동적 씬에 비현실적이라 실시간 게임 GI에 부적합하다.

**본 구현의 대체 방식**: 레이트레이싱 대신, 각 probe 위치에서 `THREE.CubeCamera`로 주변을 **6면(큐브맵) 래스터화 렌더**하여 입사 radiance를 수집한다. WebGL이 가장 잘하는 래스터화만으로 DDGI를 근사한 것.
→ **그래서 본 GI에는 BVH가 필요 없다.** (BVH는 "광선-삼각형 교차 가속"을 위한 구조인데, 래스터화 캡처에는 광선 교차 검색 자체가 없으므로.)

### 파이프라인 (gi.js)

1. **probe 격자 배치**: 공간을 덮는 3D 격자(예: 7×2×7). DDGI의 "fixed 3D grid"에 해당.
2. **probe 캡처**: 각 probe에서 CubeCamera로 6면 렌더 → 면별 평균색을 그 방향 입사 radiance로 사용(ambient-cube 형태로 6방향 저장). 슬라이드의 L1 SH 저장을 단순화한 형태.
3. **멀티바운스**: 캡처 결과를 텍스처로 머티리얼에 다시 먹여 재캡처(3패스). DDGI의 "recursive feedback / 무한 바운스 수렴"을 패스 누적으로 근사.
4. **베이크 시 톤매핑·안개 off**: 선형 HDR로 캡처해야 GI가 어둡게 눌리지 않음(중요 디테일).
5. **셰이더 적용**: `onBeforeCompile`로 MeshStandardMaterial에 주입. 픽셀 위치에서 **인접 8 probe를 트라이리니어 블렌딩**, 법선 방향으로 ambient-cube를 평가해 `indirectDiffuse`에 합산. → color bleeding(붉은/푸른 벽색이 인접 면에 번짐) 구현.

### 정적 베이크 선택

광원(방사능 단말기)이 정적이라 시작 시 1회 베이크. 동적 GI 갱신을 매 프레임 하지 않아 비용 절감. (단말기 활성화로 색만 바뀌는 것은 게임 연출이며 GI 재베이크는 하지 않음.)

### 한계 (DDGI 고유 + 보고서 논의거리)

- **probe 격자 해상도가 디테일을 제한**: 격자가 듬성하면 작은 구조에서 빛이 새거나(light leak) 뭉개짐. 강의의 "structures smaller than probe spacing may leak" 그대로.
  → 이 때문에 게임의 **감지도(노출 판정)는 GI 값이 아니라 단말기 거리+가시선으로 별도 계산**(awareness vs exposure 섹션 참조). GI는 화면 비주얼 전용.
- L1/ambient-cube는 저주파라 **diffuse만 표현, specular 불가**(DDGI 공통 한계).

## 감지도(awareness) vs 노출도(exposure)

- 노출도(빛): 단말기 근접+가시선, 손전등 → "좀비가 볼 때 보이는지"의 입력.
- 감지도(HUD): 실제로 좀비가 플레이어를 감지/수색 중인 정도. 벽에 가려 좀비가 못 보면 0.
- 소리는 벽 너머도 들림(청취 거리), 시야는 벽에 막힘(LOS).
